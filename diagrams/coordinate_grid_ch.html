What the weight hook enables (lead-in to Phase 4's live-traffic scenario)
The shortcut H1 ══30══ H11 is one number, but it's the sum of 10 underlying edges. Change any of those edges, the shortcut's cost changes, and the optimal route can flip. Typical production use-cases that plug into the same hook:
Use caseHow it plugs in
Time-of-day speed profilesswap `highwayWeights[]` at query time (rush-hour vs overnight)
Live-traffic overlaysmultiply specific edges by a congestion factor fetched from traffic feed — Phase 4 below
Vehicle typedifferent weight tables per profile (car / truck / bike)
Road closuresset an edge to +Inf — the shortcut that included it becomes invalid and CH falls back to alternate edges
Valhalla's real system does all four. This demo just needs weight-table hooks — the search code doesn't change.
Hierarchy limits (Run 3) — Valhalla's first-/last-mile rule
Each search only relaxes an edge at level L if the incoming node is within ExpandWithin[L] Euclidean distance of its home endpoint (start for FWD, goal for BWD):
LevelClassExpandWithinEffect on L1→L9 (Euclidean ≈ 32)
0local2.5only D1 from FWD and D11 from BWD reachable as locals; D6 cut off
1arterial5.0arterial near each endpoint only — A6 is too far from both
2highway∞no limit — the highway shortcut is available end-to-end
Middle arterial + D6 dimmed in Phase 3 — the hierarchy rule forbids their expansion that far from either endpoint, pushing the search onto the highway shortcut. At continental scale this is what actually gives CH its O(√n) behaviour.

All three find the same path (CH preserves optimality). On this toy graph Bi-A* looks like overhead because its two open sets need scale to amortise. At continental scale, a single H1══H11-style shortcut replaces thousands of highway edges in one relaxation, and weight tables let the same preprocessed graph serve rush-hour, overnight, and live-traffic queries — swap the weight vector per query. Phase 4 below demonstrates that last point.

Cost breakdown of the traffic route: 1.5 (L1–L2) + 1.5 (L2–A1) + 5×7 (A1..A8 free) + 8 (A8–A9 rush) + 5×2 (A9..A11) + 2.5 (A11–L9) = 58.5.
Same cost via highway would be 3 (L1–L2–A1 avoids jammed ramp) + 2 (A1–H1) + 9 (H1..H4) + 15+15 (accident) + 15 (H6..H11) + 2 (H11–A11) + 2.5 = 63.5. Arterial wins by 5.0 — the route flipped.
★ Teaching points for the classroom
  • The graph didn't change. The 18 shortcuts from Phase 2 are still there. Only four edge weights were updated.
  • The route flips in two independent places:
    • Local entry — direct L1→A1 (now jammed at 8.0) is replaced by L1→L2→A1 (3.0 via detour).
    • Backbone — highway H1══30══H11 (now effectively 54 because of the accident) is replaced by the full arterial chain.
  • Live traffic hits all 3 levels (L, A, H) on purpose — so every hierarchy layer contributes to the new optimum.
  • This is how production routers work. Feed arrives → overlay updates weights → next search picks the new optimum. No CH rebuild, no graph surgery.
  • ⚠️ A subtle note: CH + hierarchy limits (Run 3 in the Go demo) can't fully reroute here, because the arterial chain lives outside ExpandWithin[1]=5.0 from L1. At continental scale, those radii are tuned with traffic considerations in mind.
